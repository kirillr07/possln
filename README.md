# Модуль оценивания "ПОС"

Консольное приложение для учета студентов, критериев оценивания и оценок. Итоговый балл считается из текущих оценок и рубрикатора, а не хранится отдельно.

## Как запустить

Нужен .NET 9 SDK

Сборка:

```bash
dotnet build possln.sln
```

Запуск приложения:

```bash
dotnet run --project pos
```

Запуск тестов:

```bash
dotnet test
```

(все команды выполняются из корня репозитория, где лежит possln.sln)

Файлы экспорта:

- При ручном экспорте путь запрашивается в меню. Если оставить путь пустым, будет создан файл grades_export.csv в текущей папке.
- Демонстрационный сценарий создает файл demo_grades.csv в текущей папке.
- Если в пути указана несуществующая папка, приложение создаст ее автоматически.

## Что умеет приложение

В консольном меню есть такие сценарии:

1. Показать рубрикатор курса.
2. Добавить критерий в рубрикатор.
3. Показать список студентов.
4. Зарегистрировать студента.
5. Выставить или исправить оценку.
6. Отменить оценку.
7. Показать ведомость студента и рассчитать итог.
8. Показать сводную ведомость курса.
9. Экспортировать ведомость в CSV.
10. Запустить демонстрационный сценарий.
0. Выйти из программы.

Демонстрационный сценарий сам создает критерии, студентов и оценки. Он показывает, как работают инварианты, считает итог и выгружает CSV файл. Если запустить демо повторно в той же сессии, критерии уже будут существовать, поэтому повторный запуск не пройдет. Это ограничение демонстрации, а не домена.

## Доменная модель

### Единый язык предметной области

В коде используются те же слова, что и в задании:

- студент;
- критерий;
- рубрикатор;
- оценка;
- итог, или итоговый балл.

Эти слова есть в именах классов и методов: `Student`, `Criterion`, `Rubric`, `Evaluation`, `FinalGrade`.

### Агрегаты

В модели два агрегата.

**Student** является корнем агрегата. Внутри него хранятся оценки. Одна оценка относится к одному критерию. Поэтому оценки лежат в словаре по идентификатору критерия, и по одному критерию у студента может быть только одна актуальная оценка.

**Rubric** тоже является корнем агрегата. Внутри него хранятся критерии. Критерий нельзя добавить в рубрикатор дважды, даже если идентификатор отличается регистром.

Граница между агрегатами проходит по идентификатору критерия. Студент не хранит ссылку на рубрикатор и не хранит объект критерия. У оценки есть только `CriterionId`. Согласованность обеспечивает доменная фабрика и сценарий выставления оценки.

### Entity и Value Object

**Student** и **Rubric** являются сущностями, у них есть идентификатор и жизненный цикл.

**Criterion** является сущностью внутри агрегата `Rubric`. У критерия есть собственный идентификатор, по которому его находят и сравнивают. Критерий неизменяемый, но это не делает его value object, потому что важна именно его идентичность внутри рубрикатора.

**Evaluation** является сущностью внутри агрегата `Student`. Ее идентичность задается критерием: у студента не может быть двух разных оценок по одному критерию. Оценка неизменяемая. Исправление оценки создает новый объект и заменяет старый.

Value objects:

- `StudentId` хранит идентификатор студента и не разрешает пустой Guid;
- `CriterionId` хранит идентификатор критерия, обрезает пробелы и сравнивает значения без учета регистра;
- `Score` хранит балл и проверяет, что он находится в диапазоне от 0 до максимума критерия;
- `Weight` хранит вес критерия и проверяет, что он находится в диапазоне от 0 до 1;
- `FinalGrade` хранит итоговый балл, округляет его до двух знаков и ограничивает сверху значением 10.

Пример разделения: `Score` не имеет идентификатора. Два балла 5 из 10 равны как значения. А два студента с одинаковым именем остаются разными сущностями, потому что у них разные `StudentId`.

### Инварианты

Модель не позволяет нарушить основные правила предметной области.

- Идентификатор студента не может быть пустым.
- Имя студента не может быть пустым.
- Идентификатор и название рубрикатора не могут быть пустыми.
- Идентификатор и название критерия не могут быть пустыми.
- Максимальный балл критерия должен быть больше нуля.
- Вес критерия должен быть от 0 до 1.
- Балл оценки не может быть меньше нуля и больше максимума критерия.
- Оценку нельзя создать по критерию, которого нет в рубрикаторе.
- Оценка внутри студента должна относиться к тому критерию, по которому ее выставляют.
- Итоговый балл не может быть отрицательным.
- Итоговый балл ограничивается значением 10.

Часть проверок продублирована специально. Например, `Score` проверяет диапазон при создании, а `Student.SetEvaluation` дополнительно проверяет максимум критерия. Это защита от оценки, созданной по другому рубрикатору.

### Repository

Хранение вынесено из домена через порты:

- `IStudentRepository`;
- `IRubricRepository`.

Порты лежат в `Domain/Ports`. Домен не знает, где именно хранятся данные. В проекте есть только in-memory реализации в `Infrastructure/Persistence`. При необходимости можно добавить JSON или базу данных, не меняя домен.

В in-memory реализации репозиторий хранит ссылки на объекты. Поэтому изменения агрегата видны сразу. Метод `Update` оставлен в порту как часть контракта репозитория. Сейчас он фактически ничего не меняет, потому что объект в хранилище тот же самый. Для реального хранилища этот метод понадобится.

### Domain Service

Расчет итога вынесен в доменный сервис `FinalGradeCalculator`. Правило не принадлежит только студенту или только рубрикатору, потому что для расчета нужны оба агрегата.

`FinalGradeCalculator` не хранит итог. Он считает его каждый раз из текущего набора оценок и текущего рубрикатора. Поэтому итог всегда согласован с оценками.

Сам расчет делегируется стратегии `IGradeCalculationStrategy`. Сейчас используется `WeightedGradeStrategy`.

## Архитектура

Выбрана гексагональная архитектура, она же "Ports and Adapters"

Слои:

- `Domain` содержит модель, value objects, фабрику, доменный сервис и порты репозиториев.
- `Application` содержит входящий порт `IGradeSystemFacade`, его реализацию `GradeSystemFacade`, исходящий порт `IGradeExporter` и DTO для внешнего мира.
- `Infrastructure` содержит адаптеры хранения и экспорта.
- `Presentation` содержит консольное меню и вывод в консоль.
- `Program` является composition root. Он собирает зависимости через DI контейнер.

Зависимости направлены внутрь:

- `Presentation` зависит от `Application`.
- `Application` зависит от `Domain`.
- `Infrastructure` зависит от `Domain` и от портов `Application`.
- `Domain` не зависит ни от одного внешнего слоя, не знает про консоль, файлы и CSV.
- `Program` зависит от всех слоев, потому что собирает приложение.

Входящий порт `IGradeSystemFacade` описывает сценарии для внешнего мира. Консоль работает только с этим интерфейсом. Исходящий порт `IGradeExporter` описывает экспорт. Адаптер `CsvGradeExporter` реализует этот порт.

DI контейнер подключен через пакет `Microsoft.Extensions.DependencyInjection`. Регистрация зависимостей находится в `Program.ConfigureServices`.

## Паттерны GoF

В проекте ровно три паттерна, по одному из каждой группы. Больше паттернов не добавлялось специально, чтобы не делать архитектуру декоративной.

### Порождающий паттерн: Factory

Класс `EvaluationFactory` создает оценку в одном месте.

Какую боль закрывает: без фабрики оценку можно было бы создать с любым баллом и по любому критерию. Фабрика проверяет, что критерий есть в рубрикаторе, и создает `Score` с проверкой диапазона. Конструктор `Evaluation` сделан внутренним, поэтому создать оценку в обход фабрики из другого слоя нельзя.

Где используется: `GradeSystemFacade.SetStudentEvaluation`.

### Структурный паттерн: Facade

Класс `GradeSystemFacade` реализует входящий порт `IGradeSystemFacade` и дает консоли один простой интерфейс для всех сценариев.

Какую боль закрывает: консоль не должна знать про репозитории, фабрику оценок, калькулятор итога и экспортер. Вместо этого она вызывает один метод фасада, например «зарегистрировать студента» или «выставить оценку». Фасад скрывает подсистему и собирает сценарии в одном месте.

Где используется: `Presentation/ConsoleMenu.cs` вызывает только `IGradeSystemFacade`.

### Поведенческий паттерн: Strategy

Интерфейс `IGradeCalculationStrategy` и реализация `WeightedGradeStrategy` задают правило расчета итога.

Какую боль закрывает: формула итога может измениться. Например, можно добавить другую шкалу или другое правило округления. `FinalGradeCalculator` при этом не меняется, он получает стратегию через DI. Сейчас используется взвешенная сумма.

Где используется: `FinalGradeCalculator` получает `IGradeCalculationStrategy` через конструктор, регистрация находится в `Program.ConfigureServices`.

## Как считается итог

Для каждого критерия балл приводится к десятибалльной шкале:

```text
нормализованный балл = балл / максимум критерия * 10
```

Затем нормализованный балл умножается на вес критерия. Итог равен сумме таких вкладов по всем критериям. Если по критерию нет оценки, его вклад равен нулю.

Итог округляется до двух знаков и ограничивается сверху значением 10. Отрицательный итог невозможен.

Пример из демонстрации:

- домашние задания: 95 из 100, вес 0.4, вклад 3.8;
- тест: 18 из 20, вес 0.2, вклад 1.8;
- экзамен: 9 из 10, вес 0.4, вклад 3.6;
- итог: 9.2.

### Сумма весов

Сумма весов критериев в программе не проверяется. Это осознанное решение: за корректную сумму весов отвечает пользователь.

Последствия такие:

- если сумма весов больше 1, итог может превысить 10, но будет ограничен значением 10;
- если сумма весов меньше 1, максимально возможный итог будет меньше 10;
- каждый отдельный вес должен быть от 0 до 1.

Это поведение стоит учитывать при настройке рубрикатора. В README оно описано явно, чтобы не было сюрпризов.


## Принятые решения и ограничения

- В приложении один рубрикатор, он создается при запуске. Поддержка нескольких курсов оставлена на будущее.
- Данные хранятся в памяти и пропадают после выхода из программы. Это сделано для простоты и для демонстрации архитектуры.
- Редактирование и удаление критериев не реализовано. В задании это не является обязательным.
- Удаление студента не реализовано. В задании это тоже не является обязательным.
- Импорт ведомости не реализован. В обязательных сценариях задания его нет.
- В консоли студент выбирается по GUID. Для демонстрации это удобно не всегда, но позволяет однозначно указать студента.
- Экспорт по умолчанию создает файл `grades_export.csv` в текущей папке. Демонстрационный сценарий создает `demo_grades.csv`.

Что можно добавить дальше: несколько курсов, пересдачи, апелляции, постоянное хранилище, импорт ведомостей и выбор студента по номеру в списке.
